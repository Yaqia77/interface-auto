# 平台三期：API + Web + App 三合一统一自动化架构设计

> 前置：v1/v2 接口自动化（Excel 驱动）、v2 UI 自动化（JSON + Playwright）、二期登录态（storage_state）均已落地。
> 本文只解决一个问题：**如何把"接口 / Web / App"三类自动化收敛到一套统一架构上，让新增 App 自动化不是"再贴一套并行系统"，而是"接入同一个骨架"。**

## Context：现状与真正的隐患

现状是"三套执行器 + 分裂的存储/寻址"，而非统一底座：

| 维度 | 接口(api) | Web(ui) | 公共脚本(scripts) |
|---|---|---|---|
| 引擎 | `core.runner.CaseRunner` | `core.ui_runner.UiRunner` | `core.scripts.run_scripts` |
| 载体 | **Excel（canonical）** | **JSON** | JSON |
| 步骤模型 | 一行一请求（method/url/assert/extract） | `steps[]`（12 个 web 动作） | `steps[]`（4 个动作） |
| 定位/取值 | URL + JSONPath | `css=/xpath=/text=/role=` | JSONPath |
| 鉴权 | header token | **storage_state（UiSession，二期）** | request 步骤自带 |

**已经统一的部分（重要，别推翻）**：依赖编排 `dependencies.json`、测试场景 plans、定时调度 schedules、
Webhook 通知、报告归档 `allure_store`、RBAC/审计/凭证——这些**全部按 `file` 参数寻址、与引擎无关**，
是天然的共享设施层。

**真正的隐患**（三合一时会被放大）：
1. **存储二分**：api=Excel / ui=JSON，App 来了就要再造第三种 → 每种能力一套读写/校验/迁移代码，越迭代越碎。
2. **寻址靠文件后缀硬编码**：`main.py` 用 `.json→test_ui.py 否则 test_api.py` 分流；`conftest.pytest_generate_tests`
   为每种 kind 写一套分支。加 App 就是 `if/elif` 继续膨胀。
3. **定位器方言是 web 专用**：`ui_case_store._LOCATOR_PREFIXES` 只认 css/xpath/text/role；App 用
   accessibility id / iOS predicate / Android UiAutomator，语义完全不同。
4. **登录态是 web 专用**：二期 `UiSession.storage_state` 只对浏览器成立；App 用设备态/token 注入，API 用 header。

**一个已被验证的正确范式**：`core/scripts.py` 的 `ACTION_FIELDS`（动作→字段白名单）**同时驱动后端校验与前端表单**，
"绝不会出现页面能填、执行不认"。三合一就是把这套"声明式动作 + 单一 schema 源"上升为**全平台通用内核**。

## 统一论点（一句话）

> **一套「用例 = 有序步骤列表」的规范化 Schema + 一个「引擎注册表（api/web/app）」+ 三个可插拔方言
> （定位器方言 / 会话方言 / 载体适配器）**；执行/报告/调度/权限/依赖这套设施层**已经引擎无关，直接复用**。

不是把三者塞进一个巨型 if/else，而是把三个引擎实现同一个接口，公共内核只认"步骤 + 变量池 + 断言 + 提取"。

## 核心抽象

### 1) 统一用例模型（canonical = 结构化 JSON）

所有引擎共享的用例骨架（App/Web/API 都是它的实例）：

```jsonc
{
  "schema": 1,
  "case_id": "login_001",
  "project": "<项目id>",
  "engine": "api | web | app",       // ← 取代按文件后缀分流；寻址靠 kind/engine
  "platform": "web | android | ios",  // engine=app 时细分；api 可空
  "module": "登录", "name": "...", "desc": "...",
  "priority": "P0", "run": true,
  "session": "album_test_login",      // 引用「会话」抽象（见 §4），三引擎统一
  "steps": [ { "action": "...", /* 方言字段 */ "desc": "" } ],
  "extract": [ { "var": "token", "source": "<引擎方言来源>" } ],
  "pre_scripts": ["..."], "post_scripts": ["..."]   // 复用 scripts 引擎
}
```

- **接口用例的"一行一请求"被自然降维成"一个 request 步骤"**：`{"action":"request","method","url","headers","params","body","assert"}`——
  这恰好就是 `scripts.ACTION_FIELDS["request"]` 的字段集，API 引擎与脚本引擎由此合流。
- **步骤动作 + 可用字段 = 一张 `ACTION_FIELDS` 白名单**（每个引擎一份），后端校验、前端编辑器、
  meta 接口三者同源。这是 `scripts.py` 已验证模式的推广。

### 2) 引擎注册表（Engine Registry）

```python
class BaseEngine(Protocol):
    key: str                       # "api" / "web" / "app"
    ACTIONS: dict[str, set[str]]   # 动作→字段白名单（驱动校验+表单，scripts.py 同构）
    def validate_case(self, raw) -> dict: ...
    def execute(self, case, ctx, session, reporter) -> CaseResult: ...
```

- `core/engines/api.py`（迁入 `runner.CaseRunner` 逻辑）、`core/engines/web.py`（迁入 `ui_runner`）、
  `core/engines/app.py`（新增）。
- **消除 `main.py` 后缀分流**：改为 `engine = registry[case["engine"]]`；`conftest.pytest_generate_tests`
  只认 `engine` 字段，不再为每种 kind 写分支。
- 结果对象统一：`CaseResult`（扩展 `steps_trace / screenshots / attachments`），三引擎都产出它 →
  `allure_store` / 报告页 / 统计零改动复用。

### 3) 定位器方言（Locator Dialect）

把 `css=/xpath=/text=/role=` 从"web 硬编码"升级为"按 platform 的方言解析器"：

| platform | 方言前缀（示例） | 解析目标 |
|---|---|---|
| web | `css= / xpath= / text= / role=` | Playwright `page.locator / get_by_role`（现状不变） |
| android | `id= / text= / desc= / xpath= / uiautomator=` | Appium `find_element(By.*)` |
| ios | `id= / predicate= / classchain= / text=` | Appium `By.IOS_PREDICATE / IOS_CLASS_CHAIN` |

- 每个方言一个 `resolve(selector) -> 驱动定位对象`；`_LOCATOR_PREFIXES` 收敛成 `Dialect(platform).prefixes()`。
- **推荐工程约定优先**：三端都引导用稳定测试标识（web `data-testid` / android `resource-id` / iOS `accessibilityIdentifier`），
  方言里给"最佳实践前缀"打头，降低脆性定位。

### 4) 会话/鉴权抽象（Session = 二期 UiSession 的一般化）

二期 `backend/ui_session_store.py` 是 **Web 会话的第一种具体实现**；抽象出统一 `SessionProvider`：

```python
class SessionProvider(Protocol):
    def attach(self, case, ctx) -> ("payload" | None, err | None)   # 复用：给引擎注入登录态
    def collect(self, case, ctx) -> None                            # 采集：从"已登录"导出登录态
```

| engine | attach 实现 | collect 实现 | 实体 |
|---|---|---|---|
| web | `new_context(storage_state=..)`（已实现） | `context.storage_state(path=..)`（已实现） | cookies+localStorage |
| api | 注入 `Authorization: Bearer {{token}}`（登录脚本/用例提取） | 跑登录请求提 token 写会话 | token |
| app | token 注入 keystore/接口，或走 App 登录页 | 登录后导出 token / 设备态 | token/设备态 |

- 注册表条目从"web 专属字段"泛化：把 `env/browser` 扩成 `env + platform`，
  实体文件命名 `<id>__<platform>__<env>.json`（延续二期的原子写 + gitignore + 不回传正文）。
- `core.ui_runner` 已按 `session_provider(case)->(payload|err)` 解耦——**App/API 引擎接同一个回调形状即可**。

### 5) 载体适配器（把 Excel 降级为"导入/导出格式"）

- **canonical 存储 = 结构化 JSON**（与 ui_case_store 同范式：原子写 + 校验通过才落盘 + `UiXxxError(kind)`）。
- Excel / Postman / Swagger-OpenAPI / 人工评审表 → **只是 `import/export` 适配器**（复用既有
  `case_importer / openapi_import / excel_writer`），不再是运行时依赖。
- 迁移不打断现状：见「落地分期」。

## App 引擎的落地要点（新增，选型建议）

| 方案 | 优点 | 代价 | 建议 |
|---|---|---|---|
| **Appium 2 + UiAutomator2/XCUITest** | 跨 Android/iOS、生态成熟、与"步骤解释器"契合 | 环境重（SDK/Xcode）、稳定性调优成本高 | **推荐主选**：与 Playwright 同属"driver 解释器"，最贴合本架构 |
| Maestro | YAML 声明、上手快、自带容错 | 动作/定位方言与现模型需映射、定制弱 | 可选轻量替代或作 PoC |
| 原生（Espresso/XCUITest） | 最稳 | 绑定语言、跨端不可、脱离平台 | 不建议纳入统一平台 |

App 独有能力（二期/三期再补，不阻塞统一架构）：设备管理（真机/模拟器/云真机 farm）、
App 安装与包版本、`webdriverio`/capability 配置、Toast/弹窗/权限对话框动作、图片断言。
这些都以**新增 App 动作 + App 方言**的形式接入，不动内核。

## 复用不变的设施层

以下**已经是引擎无关、按 `file`/`project` 寻址**，三合一后近乎零改动：
执行中心 runs（子进程跑 `main.py`）、定时调度、plans、依赖 `dependencies.json`、
Webhook 通知、`allure_store` 报告与脱敏、统计报表、RBAC/审计/凭证。
唯一改动：把"按后缀/kind 分流"换成"按 `engine` 字段查注册表"。

## 落地分期（增量、非破坏，每阶段独立可回归）

- **阶段 0｜抽象就位（不改行为）**：把 `runner/ui_runner` 包进 `engines/{api,web}.py`，实现 `BaseEngine`；
  `main.py`/`conftest` 改为查注册表，但 api 仍读 Excel、ui 仍读 JSON（引擎内各自适配）。目标=**分流机制统一，行为零变**。
- **阶段 1｜统一用例 Schema**：定义 canonical JSON step 模型 + 每引擎 `ACTION_FIELDS`；
  给 Excel 用例加"→统一模型"的**读取适配**（Excel 仍是源，运行时先转统一模型再交引擎）。前端步骤编辑器按
  `scripts.py` 的 `ACTION_FIELDS` 驱动方式，三引擎共用一套编辑器组件。
- **阶段 2｜会话 & 定位方言泛化**：`UiSession` 抽象为 `SessionProvider`（web 保持、api 补 token 实现）；
  `_LOCATOR_PREFIXES` 重构为 `Dialect(platform)`。
- **阶段 3｜App 引擎接入**：新增 `engines/app.py`（Appium）+ android/ios 方言 + App 动作集 + app 会话实现；
  项目 `kind` 扩为 `api|web|app`。**此时三合一才真正长出第三条腿，且内核未动**。
- **阶段 4｜存储收敛**：新用例一律走 canonical JSON；Excel 彻底降级为导入/导出；历史 Excel 项目按需渐进迁移。

## 兼容性与风险

- **风险1｜为统一而过早抽象**：阶段 0/1 只做"分流统一 + schema 就位"，不强制迁移存量数据，避免大面积回归。
  存量 api(Excel)/ui(JSON) 与定时任务/场景/历史批次**零影响**（沿用默认项目原地指向的既有策略）。
- **风险2｜App 稳定性**：App 自动化 flaky 远高于 Web；须同时引入**失败重试策略 + trace/录屏**（Playwright/Appium 都原生支持），
  否则企业落地即被"红海"淹没。建议 App 引擎上线即带"重试 N 次 + 隔离区(quarantine)"开关。
- **风险3｜能力对齐偏差**：三端方言/动作能力天然不等（App 无 cookie、Web 无设备态）。用
  "每引擎一张 `ACTION_FIELDS` + meta 接口下发"保证**页面能填 = 后端能跑 = 报告能展示**，杜绝口径漂移。
- **护栏**：新增引擎 = 实现 `BaseEngine` + 注册 + 提供方言，不改内核与设施层；把"加一种自动化"的成本
  从"复制一套系统"降到"实现一个接口"。
